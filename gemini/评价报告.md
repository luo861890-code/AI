## 三、实跑发现的缺陷清单（按严重度）

### 🔴 P0-1 `repair_geometries()` 静默丢弃 12/17 个地市
**位置**：`calibration/topology_calibrator.py:72` + `:76`
**机制**：`make_valid()` 对自相交 MultiPolygon 返回 **`GeometryCollection`**；下一行 `geom_type.isin(["Polygon","MultiPolygon"])` 把它们**全部过滤掉**。
**实测**：
```
输入 17 个地市 → make_valid 后 12 个变 GeometryCollection → 修复后只剩 5 个
```
**后果**：`admin_prov.png` 湖北省只剩 5 个色块，其余 12 个市**整块消失**，接口仍 `status=success`、`carto_score=100`。
**修复**（已验证有效，一处改动即 17/17 恢复）：
```python
mv = make_valid(g)
if isinstance(mv, GeometryCollection):
    polys = [p for p in mv.geoms if isinstance(p, (Polygon, MultiPolygon))]
    parts = [q for p in polys for q in (p.geoms if isinstance(p, MultiPolygon) else [p])]
    mv = MultiPolygon(parts)
```

### 🔴 P0-2 中文渲染为豆腐块 □□□（且静默）
**位置**：`renderers/base_renderer.py:27-34`
**机制**：`detect_cjk_font()` 用 `f.name in fm.fontManager.ttflist` 判存在 —— 这是**缓存列表**，可能含文件已不存在的条目。
**实测**：注入一条失效的 `WenQuanYi Micro Hei` 条目 → 选中该字体 → **8 条 missing-glyph 警告** → 全部中文变 □，而 `savefig` 照常成功。
**同一份代码同一台机器，第一次跑出豆腐块、第二次跑出正常中文** —— 因为 `~/.matplotlib/fontlist-v3.11.0.json` 在两次之间被重建。
**更糟的是**：哈基米的首选列表 `["Noto Sans CJK JP", "Noto Serif CJK JP", "WenQuanYi Micro Hei", "SimHei", "DejaVu Sans"]` **前三项全是 Linux 字体**，Windows 上真正可用的 `Microsoft YaHei`/`SimHei` 排在第 4 位，一旦缓存污染就必中招。
**修复**（已验证）：
```python
for n in ["Microsoft YaHei", "SimHei", "Noto Sans SC", "SimSun", "DejaVu Sans"]:
    try:
        fm.findfont(FontProperties(family=n), fallback_to_default=False, rebuild_if_missing=False)
        return n
    except Exception: continue
```

## 六、哈基米方案的根本性架构问题

哈基米把制图理解成"**后端 matplotlib 出一张静态 PNG**"；而本仓库的制图是"**后端产出 GeoJSON + Leaflet style JSON，前端 Leaflet 实时渲染**"。

| 维度 | 哈基米方案 | 本仓库现状 | 冲突 |
|---|---|---|---|
| 渲染位置 | 后端 matplotlib | 前端 Leaflet | **两套渲染器** |
| 依赖 | geopandas/matplotlib/pyproj | 只有 shapely | 需新增 3 个重依赖 |
| 比例尺 | 任务书里一个数字 | 运行时由 `map.getZoom()` 决定 | **静态 PNG 无法缩放** |
| 对话改图 | 改 style 再出一张 PNG | 改 Leaflet layer style | 语义可映射，但要重写 |
| 用户核心诉求"地图能缩放" | 只能预先渲染 3 张 | 原生支持 | **PNG 路线根本满足不了** |

**这决定了"最最重要"的需求（缩放改比例尺、要素随比例尺增减、道路粗细随比例尺、长江面状）必须在现有 Leaflet 侧实现**，而不是引入 matplotlib 引擎。这也正是仓库已经做对的地方：
- `map-lod.js` 已有**五档 LOD**（`_lodVisible` L133）+ **载负量预算**（300/800/2500/7000/∞，L24-37）+ **符号随缩放因子** `_symbolZoomFactor`
- `map.js` 已有**真比例尺解算**（`_computeScaleData` L1441，1px=0.0002646m @96dpi）+ `_niceScale` + `_zoomForScale`

**缺的只有两件事**：
1. **道路线宽随比例尺连续变化**（现在是固定 `weight`）
2. **行政层级下钻**（省→市→区，按视口 bbox 决定加载哪一级政区层）

## 七、给哈基米方案的一句话裁决

> **保留它的地图学知识与 6 个纯算法函数，丢弃它的渲染层、依赖与流水线。**
> 把「四色邻接 + Fisher-Jenks + Töpfer + Chaikin + 八方位注记 + 数据溯源」这 6 个算法，
> 以**纯函数**形式嫁接到仓库既有的 `map_service → Leaflet style JSON` 链路上；
> 把「多比例尺下钻 + 路宽随比例尺」做在**前端 Leaflet** 里；
> 修掉 3 个 P0 缺陷后，代码可以进主干；不修则**一张图都不能进结题材料**。
